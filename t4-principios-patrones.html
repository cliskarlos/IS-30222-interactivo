Principios y patrones de diseño

Un diseño puede funcionar y aun así ser un desastre de mantener. Aquí practicas a detectar qué principio se incumple, a elegir el patrón que resuelve un problema (o ninguno) y a ver por qué Liskov importa.

¿Un cuadrado es un rectángulo?

En geometría sí. En diseño orientado a objetos, depende del contrato. El cliente de abajo fue escrito pensando en Rectangulo. Ejecútalo con cada objeto.

class Rectangulo {
  void setAncho(int a) { ancho = a; }
  void setAlto(int h)  { alto = h; }
  int area()           { return ancho * alto; }
}
class Cuadrado extends Rectangulo {
  void setAncho(int a) { ancho = a; alto = a; }
  void setAlto(int h)  { ancho = h; alto = h; }
}

// Cliente: confía en el contrato de Rectangulo
void ajustar(Rectangulo r) {
  r.setAncho(5);
  r.setAlto(4);
  assert r.area() == 20;
}

Qué ha pasado

El contrato de setAncho en Rectangulo dice, sin escribirlo, que solo cambia el ancho. Cuadrado lo rompe: al fijar el ancho también cambia el alto. El cliente no ha hecho nada mal y aun así falla con una subclase. Eso es justo lo que prohíbe el principio de sustitución de Liskov: una subclase debe poder usarse donde se espera su clase base sin que el cliente note la diferencia.

Arreglos habituales: no hacer que Cuadrado herede de Rectangulo, sino que ambos implementen una interfaz Figura con area(); o hacer las figuras inmutables (sin setters), de modo que no haya contrato que romper.
